# Plan for #6: Add PATCH /api/runs/:id/status with allowed transitions

## Goal
A run's status can move from `planned` to `running` and from `running` to `done` via a new endpoint. Any other transition is rejected with 409; an unknown run id is rejected with 404. Existing endpoints and run creation behavior do not change.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- Confirmed: `src/runs.ts` `RunStore` holds runs in a `Map` and exposes `get`/`create`; needs a transition method and a `TransitionError`; change: yes.
- Confirmed: `src/app.ts` registers routes and the shared error handler mapping `ValidationError` to 400; needs a new `PATCH /api/runs/:id/status` route and a 404/409 mapping; change: yes.
- Confirmed: `test/app.test.ts` is the only test file covering the API and uses `supertest` against `createApp`; change: yes, add tests for happy path, invalid transition, unknown id.
- Confirmed: `README.md` API table documents each route and its errors; change: yes, add the new endpoint row.
- Confirmed: `src/config.ts` / `k8s/configmap.yaml` are unrelated to this change (no new env vars); change: no.
- Plausible: `public/index.html` does not currently show or change run status; change: no, out of scope for this ticket (UI not mentioned in "Done when").

## Tests
- `test/app.test.ts`: add a `describe("status transitions")` block:
  - happy path: `PATCH /api/runs/:id/status` with `{status:"running"}` on a `planned` run returns 200 and updated status, then `{status:"done"}` on the now-`running` run returns 200.
  - invalid transition: `{status:"done"}` directly on a `planned` run returns 409 with `error: "invalid transition"`, `from: "planned"`, `to: "done"`.
  - unknown id: `PATCH /api/runs/run-9999/status` returns 404.

## Environment contract
- No new or changed environment variables; no changes to `src/config.ts`, `k8s/configmap.yaml`, or the README environment table.

## Risks
- Must reject unrecognized `status` values in the body (not just disallowed transitions) with a clear error, without conflicting with the 409 "invalid transition" contract; treat unknown/invalid status strings as an invalid transition too since the ticket only specifies 409 for disallowed transitions and 404 for unknown id.
- Order of checks matters: id lookup (404) must happen before transition validation (409).
- Pipeline risk is limited to unit tests; no UI/e2e change means no browser check impact.

- No additional decision needed; the ticket is explicit about the two required checks and the 404/409 shape.
