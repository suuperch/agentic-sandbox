# Plan for #4: Filter runs by vehicle on the web page

## Goal
Users can type a vehicle ID above the runs table on `/` and immediately see only matching rows. Existing API behavior, run creation, and clearing the input showing all rows remain unchanged.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- Confirmed: `public/index.html` renders the runs table, fetches `/api/runs`, and owns the client-side DOM update; change: yes.
- Confirmed: `e2e/smoke.spec.ts` covers the page and run creation with Playwright locators; change: yes, add a browser test for filtering.
- Confirmed: `src/app.ts` already supports `GET /api/runs?vehicleId=...`; change: no because the issue allows client-side filtering.
- Confirmed: `src/runs.ts` seeds two `WVW-1001` rows and other vehicle IDs, giving deterministic filter data; change: no.
- Confirmed: `test/app.test.ts` already covers API filtering; change: no.
- Confirmed: `README.md` documents API filtering and browser-test expectations; change: no.
- Open: none.

## Tests
- `e2e/smoke.spec.ts`: add a test that opens `/`, types `WVW-1001` into `Filter by vehicle`, asserts only the two `WVW-1001` rows are visible, then clears the input and asserts all seeded rows return.

## Environment contract
- No new or changed environment variables; `src/config.ts`, `k8s/configmap.yaml`, and the README environment table stay out of scope.

## Risks
- Browser test can fail if the page uses CSS-hidden rows but the locator counts hidden rows; use visible row assertions.
- Existing add-run test can fail if the new filter input conflicts with the existing `Vehicle ID` placeholder/label locators.
- Pipeline risks are limited to browser tests in `deploy-kind`; unit, rollout, stability, and smoke should be unaffected.

## Open questions
1. None.

## Decisions
- No additional decision needed; the ticket is explicit and client-side filtering matches the issue.
